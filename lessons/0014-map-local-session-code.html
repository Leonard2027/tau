Micro lesson 14 · Local session code map · About 15 minutes

Session 是插件 handler 处理出来的吗？持久化又读什么？

不是。插件和 CodingSession 是 harness 事件的两条消费者路径；真正决定持久化、恢复、分支和压缩的是 CodingSession，它每次从 harness.messages 的积压快照落盘，而 tau_agent.session 提供可复用的数据、存储、路径和 replay 原语。本节建立文件地图并打通“yield 之后怎么变成持久化”。

先预测 两条事件路径 积压快照 append-lag 可复用核心 产品编排 检索练习 术语表 下一节：恢复

0–3 分钟：先判断谁拥有持久化

假设把这行代码移除：

请先预测：

  2. CodingSession.prompt() 还能迭代 harness events 吗？

  4. 一条 MessageEndEvent 触发持久化时，写的是当前事件里的那条消息，还是别的什么？

插件观察与扩展

ExtensionRuntime 通过 harness.subscribe(...) 注册 listener。它把核心 turn events 适配成 extension-facing events，再逐个调用插件 handler。

Iterator path

Session 生命周期编排

CodingSession 直接 async for harness。它在完整消息边界执行持久化，并负责 load、branch、compact、provider/runtime refresh。

关键结论：session 不是插件 handler 的产物。插件先收到事件，所以慢 handler 会延迟 CodingSession 收到事件；但 durable transcript 的写入逻辑位于 CodingSession，不位于 extension handler。

5–7 分钟：持久化读的是积压快照，不是当前事件

src/tau_coding/session.py:1504–1606, 1765–1785

_persist_messages_since 是持久化的唯一真实写入点。它从不看事件里的 .message，只看 harness 的内存 transcript 快照：

# session.py:1772
new_messages = self._harness.messages[persisted_count:]
for message in new_messages:
    entry = MessageEntry(parent_id=self._last_parent_id, message=message)
    await self._append_session_entry(entry)
    self._last_parent_id = entry.id
    leaf = LeafEntry(parent_id=entry.id, entry_id=entry.id)
    await self._append_session_entry(leaf)

persisted_count 在调用 prompt 前初始化为 len(harness.messages)（session.py:1561），每次 persist 后推进。

积压快照模型：persist 是“把 harness.messages[persisted_count:] 里新增的消息成批落盘”，而不是“处理当前事件”。它滞后一拍、成批、从 messages 取快照。三个相关指针：
  • harness.messages — 运行时 transcript（唯一数据源）
  • _last_parent_id — 追加游标：下一条新 entry 的 parent
  • persisted_count — 已持久化到第几条，下次从它之后继续

7–10 分钟：append-lag —— 消息进入 messages 晚于它自己的 MessageEndEvent

src/tau_agent/loop.py:60–168, 189–220, 225–283

这是最容易理解反的地方。loop 里，消息 append 进 messages 的时刻，晚于它自己的 MessageEndEvent：

  • assistant 消息：loop.py:132 的 messages.append(assistant) 发生在 _assistant_events 整个消费完之后；而 MessageEndEvent 是 _assistant_events 先 yield 出来的（loop.py:213/217）。
  • tool result 消息：_execute_tool_call 先 yield MessageEndEvent（loop.py:282），之后才在 loop.py:155 messages.append(...)。

一次 user → assistant(带工具) → tool result → assistant 的完整时间线

为什么每条都“晚一个边界”：JSONL 最终顺序完全正确（user, assistant1, tool1, assistant2），但每条都在它自己的 MessageEndEvent 的下一个边界才写入。session.py:1606 run 结束后的那次 persist 不是保险措施，是必需的——它专门捕捉最后一条没有后继边界的消息。

10–12 分钟：先读 tau_agent.session 的可复用核心

不要一上来从两千多行的 tau_coding/session.py 顶部往下读。先按下面顺序掌握五个原语，再看产品层怎样把它们组装起来。

  1. session/__init__.py：公开地图入口

    src/tau_agent/session/__init__.py:1–50

    只看 exports，先知道 session 包对外提供哪些 entry、storage、JSONL、tree 与 state 原语。它适合作为目录，不负责机制。

  2. entries.py：durable nouns

    src/tau_agent/session/entries.py:25–114

    定义日志里可以出现什么：message、model/thinking change、compaction、branch summary、label、leaf、session info、custom。所有 entry 共享 id、parent_id、timestamp。

  3. storage.py：append/read port

    src/tau_agent/session/storage.py:12–42

    SessionStorage 只有 append(entry) 与 read_all()。JsonlSessionStorage 是本地实现。因此“把 JSONL 换成 SQLite”首先是替换这个 port 的实现，而不是改 harness。

  4. jsonl.py：wire format 与旧数据迁移边界

    src/tau_agent/session/jsonl.py:12–111

    负责一条 entry 与一行 JSON 之间的转换；读取旧 Tau-v1 message 时，也在这里迁移成当前 canonical shape。运行时模型不承担历史兼容。

  5. tree.py：选择一条 ancestry path

    src/tau_agent/session/tree.py:12–40

    entries_by_id() 建索引并拒绝重复 ID；path_to_entry() 从 leaf 沿 parent_id 回到 root，检测缺失 parent 与 cycle，再反转成 root-to-leaf。

  6. memory.py：纯 replay reducer

    src/tau_agent/session/memory.py:21–136

    SessionState.from_entries() 把“全部 entries 或指定 path”reduce 成当前 messages、model、thinking level、label、active leaf 与 compaction state。这里不执行工具、不调用插件，也不管理 UI。

portable core 的边界：entries.py 定义事实，storage.py 保存/读取事实，jsonl.py 定义持久化格式，tree.py 选择事实路径，memory.py 把路径解释成当前状态。

12–14 分钟：再按职责切片读 tau_coding

1 · CodingSession.load()：恢复并装配新 runtime

src/tau_coding/session.py:296–405

读取 entries，找最新 leaf，replay 成 SessionState，用 state.messages 新建 AgentHarness，持久化 interrupted-tool repairs，最后绑定 extension runtime。注意顺序：先恢复 state/harness，后绑定插件 listener。

2 · prompt() + _persist_messages_since()：决定何时 durable

src/tau_coding/session.py:1504–1606, 1765–1785

prompt() 消费 harness iterator。每当看到完整的 MessageEndEvent，它调用 _persist_messages_since()，为 harness.messages[persisted_count:] 里的新消息依次 append MessageEntry 和 LeafEntry（积压快照模型，见上一节）。

3 · branch_to_entry() 与 compaction：移动 active leaf 并替换 harness messages

src/tau_coding/session.py:503–567, 1410–1421, 1961–2085

分支可选生成 BranchSummaryEntry，append 新 LeafEntry，按目标 path replay state，再调用 harness.replace_messages(state.messages)。压缩 append CompactionEntry + LeafEntry，replay 时替换旧消息。两者都不删除旧日志。

4 · session_manager.py：resume 列表，不是 transcript

src/tau_coding/session_manager.py:15–180

维护 session ID、JSONL path、cwd、model、title、更新时间等索引元数据。它回答“有哪些 session、文件在哪里”，不负责从 transcript log 恢复 messages。

14–15 分钟：只回答“先看哪里 + persist 写什么”

设当前正处于一个 tool cycle：_execute_tool_call 刚把 MessageEnd(tool1) yield 给 CodingSession，CodingSession 正在处理它。此前 prompt 已经持久化，这是第一个工具调用。此时 harness.messages = [user, assistant1]。

  1. 此刻 harness.messages 里有哪几条消息？tool1 在不在？
  2. 这一次 _persist_messages_since 会往 JSONL 写哪几条消息？为什么不是 tool1？
  3. 新增一种 durable entry 类型，先看哪里？
  4. 把本地 JSONL 存储替换成 SQLite，主要实现哪个 port？
  5. 根据 active leaf 恢复 root-to-leaf path，在哪里？把 path reduce 成 messages/model/compaction state，在哪里？
  6. 决定何时 persist、branch、compact，并重建 harness，在哪里？
  7. 插件 handler 和 session 持久化之间是什么关系：生产者，还是同一 harness event 的另一条消费者路径？
回答后展开参考答案
  1. [user, assistant1]。tool1 还没被 append 进 messages（它在 loop.py:155 才追加，晚于它自己的 MessageEndEvent）。
  2. 写 assistant1。因为 persist 只读 messages[persisted_count:] 的积压快照，此刻 assistant1 是唯一已落进 messages 的新消息；tool1 连 messages 都还没进。这就是“滞后一拍、成批、快照”模型。
  3. tau_agent/session/entries.py；随后检查 union、serialization 与 replay 是否需要适配。
  4. storage.py 的 SessionStorage port。
  5. tree.py:path_to_entry()；memory.py:SessionState.from_entries()。
  6. tau_coding/session.py:CodingSession 的对应职责切片。
  7. 另一条消费者路径。插件先经 _notify 收到事件，CodingSession 随后经 harness iterator 收到事件并自行持久化。
