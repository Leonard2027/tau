为什么 loop 不直接操作 UI？

本节研究 run_agent_loop 的输出端：它不写屏幕、不存日志、不推 WebSocket——它只 yield 事件。为什么？事件有哪几层？

先预测 源码切片 分层练习 追踪发射点 一句话复述 完整路线

0–3 分钟：先预测

你已知道 run_agent_loop 是一个 async generator，也知道 harness 的 listeners 用 for listener in listeners: await listener(event) 顺序通知。

思考两个问题：

  1. 如果 loop 直接调用 tui.render() 或 logger.write()，会引入什么耦合？
  2. 一次包含工具调用的完整 agent run，你猜至少需要哪几种事件？（只凭直觉列）

3–8 分钟：读事件层级

src/tau_agent/events.py:15–87

整个文件只有 10 个事件类和一个联合类型。按粒度从粗到细分成四层：

Agent 层

整个 run 的边界

AgentStartEvent 和 AgentEndEvent。一个 run 只发出一对。AgentEndEvent.messages 携带本次 run 新增的全部消息。

Turn 层

一轮模型调用的边界

TurnStartEvent 和 TurnEndEvent。如果模型调了工具，loop 循环一次就多一对 turn 事件。TurnEndEvent 携带这一轮的 assistant message 和 tool results。

Message 层

单条消息的生命周期

MessageStartEvent、MessageUpdateEvent、MessageEndEvent。无论是 prompt、assistant 回复还是 tool result，都经过同一组消息事件。

Tool 层

工具执行进度

ToolExecutionStartEvent、ToolExecutionUpdateEvent、ToolExecutionEndEvent。嵌套在一轮 turn 内部，每个 tool call 一组。

联合类型：AgentEvent

type AgentEvent = Annotated[
    AgentStartEvent | AgentEndEvent
  | TurnStartEvent | TurnEndEvent
  | MessageStartEvent | MessageUpdateEvent | MessageEndEvent
  | ToolExecutionStartEvent | ToolExecutionUpdateEvent | ToolExecutionEndEvent,
    Field(discriminator="type"),
]

所有事件共享一个 type 字段作为判别器，consumer 用 isinstance 或 event.type 就能分流。

设计意图：loop 只产出 AgentEvent，不知道谁在消费。TUI 渲染、CLI 日志、测试断言、WebSocket 推送——都是同一个 event stream 的不同 listener。

8–12 分钟：分层练习

把下面 10 个事件按四层（Agent / Turn / Message / Tool）分类：

AgentStartEvent    TurnStartEvent    MessageStartEvent    ToolExecutionStartEvent
AgentEndEvent      TurnEndEvent      MessageUpdateEvent   ToolExecutionUpdateEvent
                                     MessageEndEvent      ToolExecutionEndEvent

然后回答：

  1. 哪一层的事件在一次纯文本回答（没有工具调用）中不会出现？
  2. MessageUpdateEvent 嵌套了一个 assistant_message_event 字段。它的类型是什么？为什么需要嵌套？
  3. TurnEndEvent 既携带 message 又携带 tool_results——这两者的关系是什么？
回答后展开参考答案

1. Tool 层——纯文本回答不触发工具执行，三个 ToolExecution* 事件都不会出现。

2. AssistantMessageEvent（来自 provider_events.py）。嵌套是因为 agent 层需要把厂商无关的 provider streaming 事件（text delta、thinking delta、tool call 等）透传给下游 consumer，同时保持 agent event 接口统一。consumer 可以只看 MessageUpdateEvent，也可以深入看嵌套的 provider event 做更细粒度的处理。

3. message 是这一轮的 AssistantMessage（里面可能包含 ToolCall content blocks）；tool_results 是 loop 执行工具后收集的 ToolResultMessage 列表。它们是同一轮的因果关系：模型发出请求（message），loop 执行后返回结果（tool_results）。

关键发现：tool execution 事件和 tool result message 事件是不同层的东西。ToolExecutionEndEvent 是执行进度通知（tool 层），紧跟着的 MessageStart/EndEvent 是把结果写入消息历史（message 层）。两者都在 _execute_tool_call 内发出，但语义不同。

14–15 分钟：一句话检索

run_agent_loop 不操作任何外部系统，而是 yield ______ 类型的事件；这些事件分成 ______、______、______、______ 四层。
面试表达：事件流是 loop 与外部世界唯一的输出通道。这实现了关注点分离：同一个 loop 可以驱动 TUI、CLI、HTTP API 或测试，只需要不同的 listener 订阅同一个 AgentEvent stream。

两层事件的关系

provider events vs agent events

provider_events.py (12 种)    events.py (10 种)
──────────────────────────    ──────────────────
AssistantStartEvent      →   MessageStartEvent
TextDeltaEvent           →   MessageUpdateEvent (嵌套原始 provider event)
ThinkingDeltaEvent       →   MessageUpdateEvent
ToolCallEndEvent         →   MessageUpdateEvent
AssistantDoneEvent       →   MessageEndEvent
AssistantErrorEvent      →   MessageEndEvent

转换发生在 src/tau_agent/loop.py:189–223 的 _assistant_events()

Provider events 是模型流的原始粒度（text chunk、thinking chunk、tool call fragment）；Agent events 是 loop 暴露给外部的统一接口。_assistant_events() 做了一次协议抬升。

主来源

src/tau_agent/events.py 定义 agent event 层级；src/tau_agent/provider_events.py 定义 provider event 层级；src/tau_agent/loop.py:64–68, 189–223, 225–282 是事件的发射位置；tests/test_agent_loop.py:54–83 验证最短事件序列。
