本地 coding agent 的流式事件怎样到达 TUI？

Tau 当前是单机、进程内 coding agent。本节不虚构网络客户端，而是追踪一个 text_delta 从 provider 到 loop、harness、extension、CodingSession，最后到 TUI/CLI 的真实路径。

先预测 真实链路 两条消费路径 为什么有意义 顺序练习 完整路线

0–3 分钟：预测一个 delta 的去向

provider 产生：

TextDeltaEvent(
    content_index=0,
    delta="Hel",
    partial=AssistantMessage(...)
)

请先预测：

  1. loop 会把它原样直接交给 TUI 吗？
  2. extension 和 TUI 谁先收到同一个事件？
  3. 这个 delta 会立即作为一条 durable message 写入 session 吗？

3–8 分钟：沿产品装配追踪完整路径

1 · Provider → loop

src/tau_agent/provider.py · provider_events.py · loop.py:189–222

provider.stream_response()
    ↓ TextDeltaEvent(delta="Hel")
run_agent_loop._assistant_events()
    ↓ MessageUpdateEvent(
          message=partial,
          assistant_message_event=TextDeltaEvent(...)
      )

loop 没有把某个厂商 SDK 的原始 chunk 直接泄漏给产品层。它把 provider-neutral 的增量事件嵌进稳定的 MessageUpdateEvent。

2 · loop → harness

src/tau_agent/harness.py:161–196

async for event in run_agent_loop(...):
    await self._notify(event)   # 先给本地 extension listener
    yield event                 # 再给主 async-iterator 消费者

harness 没有向网络发送事件。它只在同一进程内做两件事：同步等待订阅者，然后把事件交给拉取 prompt() 的调用方。

3 · harness listener → ExtensionRuntime

src/tau_coding/session.py:367–399 · extensions/runtime.py:489–496, 818–849

CodingSession.load()
    ↓ harness.subscribe(runtime._on_agent_event)
ExtensionRuntime._on_agent_event(event)
    ↓ runtime.emit_event(event)
extension handlers

这是 harness 的 subscription path。extension 可观察或响应 agent events；由于 harness 会 await listener，慢 extension handler 会延迟后面的主迭代路径。

4 · harness yield → CodingSession

src/tau_coding/session.py:1504–1717

persisted_count = len(self._harness.messages)
events = self._harness.prompt_message(...)
async for event in events:
    if isinstance(event, MessageEndEvent):
        persisted_count = await self._persist_messages_since(persisted_count)
    ...
    yield event

CodingSession 是主要迭代消费者。MessageEndEvent 只是触发持久化检查；_persist_messages_since() 实际读取的是 harness.messages[persisted_count:] 的积压快照，而不是直接保存当前事件的 message。当前 assistant/tool-result 通常尚未 append，会在后一个边界写入；完整时序见 第 14 节的 append-lag。随后 session 继续处理错误、加入 session-owned events，并向产品界面 re-yield。

5 · CodingSession → TUI 或 CLI

src/tau_coding/tui/app.py:4510–4686 · tui/adapter.py:24–99 · cli.py:692–766

# TUI
async for event in self.session.prompt(...):
    self.adapter.apply(event)
    self._apply_streaming_transcript_event(event)

# print mode
async for event in session.prompt(prompt):
    renderer.render(event)

TUI 把事件应用到 TuiState 并更新 transcript widgets；print mode 则把同一 session event 交给 text/JSON/transcript renderer。

8–10 分钟：不要混淆两条本地消费路径

Subscription path

harness → extensions

_notify 先顺序等待 listeners。生产装配中主要 listener 是 ExtensionRuntime._on_agent_event。

Iterator path

harness → session → UI

调用方通过 async for 拉取事件。CodingSession 先处理和持久化，再 re-yield 给 TUI 或 CLI。

精确顺序：loop yield → harness 等待 extension listeners → harness yield → CodingSession 处理/re-yield → TUI/CLI 渲染。这里所有箭头都是本地进程内调用。

10–12 分钟：这层事件设计对本地 Tau 有什么意义？

  1. 隔离 provider 与产品界面

    TUI 不必理解 Anthropic、OpenAI 或其他 SDK chunk，只理解 Tau 的 AgentEvent 与嵌套的 provider-neutral assistant events。

  2. 同一事件支持多种本地产品形态

    TUI、print mode、JSON renderer、benchmark 和 extensions 可以使用同一核心事件契约，不需要把显示逻辑塞进 loop。

  3. 区分增量显示与最终持久化

    MessageUpdateEvent 让 UI 实时显示；完整 MessageEndEvent 是 CodingSession 检查持久化的语义边界，但当次写入来自 harness.messages 的 backlog snapshot，不等于直接保存当前事件携带的消息。

  4. 看见本地背压的真实来源

    慢 extension 会卡在 harness 的 await _notify；慢 TUI/renderer 则会因为 async iterator 是拉取式而延迟请求下一事件。两者都会让 provider stream 暂停推进。

12–14 分钟：排出一个 delta 的真实顺序

请把下面步骤按实际顺序排列：

  1. TUI adapter 将事件应用到 TuiState
  2. ExtensionRuntime handler 收到事件
  3. provider 产生 TextDeltaEvent("Hel")
  4. CodingSession 收到并 re-yield 事件
  5. loop 产生嵌套该 delta 的 MessageUpdateEvent
  6. harness 把事件 yield 给主迭代者

再回答：如果 extension handler 处理 5 秒，TUI 何时能看到 "Hel"？

回答后展开参考答案

顺序是 3 → 5 → 2 → 6 → 4 → 1。extension path 发生在 harness yield 之前；如果 handler 用时 5 秒，TUI 至少要等这 5 秒后才能收到该事件。
