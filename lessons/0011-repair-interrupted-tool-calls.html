Micro lesson 11 · Reliability · About 15 minutes

取消后，为什么必须修复孤儿工具调用？

当 assistant 已经产生 tool call，但取消发生在 tool result 写回之前，历史中会留下一个未闭合的协议请求。Tau 不删除历史，也不擅自重试工具，而是追加一条可关联、可重放的错误结果。

先预测 对象追踪 协议不变量 可靠性练习 完整路线

0–3 分钟：选择恢复策略

当前消息历史已经持久化：

UserMessage("Read README.md")
AssistantMessage(
    text="I'll read it",
    tool_calls=[ToolCall(id="call-1", name="read", ...)]
)
# 此时用户取消；call-1 没有 ToolResultMessage

下一次 continue_() 或新 prompt 开始前，host 应该怎么处理？

  1. 删除包含 tool call 的 assistant 消息
  2. 自动重新执行 read 工具
  3. 追加与 call-1 关联的错误结果
  4. 什么都不做，让 provider 自己判断

先选一个，再回答：你的策略在“工具具有外部副作用”时是否仍然安全？

3–8 分钟：追踪 call-1 的补偿记录

src/tau_agent/harness.py:146–190, 219–244

AssistantMessage 历史中已存在 ToolCall(id="call-1")，代表模型请求执行工具。
Cancellation 运行结束或进程恢复时，历史里尚无相同 ID 的结果。
ToolResultMessage 追加 tool_call_id="call-1"、is_error=True 的中断结果。

修复算法

returned_ids = {
    result.tool_call_id
    for result in messages
    if isinstance(result, ToolResultMessage)
}

for assistant in messages:
    for call in assistant.tool_calls:
        if call.id not in returned_ids:
            messages.append(
                ToolResultMessage(
                    tool_call_id=call.id,
                    tool_name=call.name,
                    content="Tool call interrupted by user",
                    is_error=True,
                )
            )

关联键仍是前面课程学过的不变量：ToolResultMessage.tool_call_id == ToolCall.id。

这是补偿，不是重试：修复记录只声明“这次调用没有成功完成”。它不会再次执行工具，因此不会重复发送邮件、扣款、写文件或触发部署。

8–10 分钟：可靠性不变量

Completeness

每个 call 都有终态

对历史中的每个 ToolCall.id，都应能找到对应结果：成功结果或明确的错误/中断结果。

Idempotency

修复可以重复运行

returned_ids 会跳过已有结果；同一个修复算法再次执行时，不会为同一 call 追加第二条中断结果。

Auditability

保留发生过的事实

删除 assistant 消息会改写历史。追加错误结果保留“模型确实请求过工具，但执行被中断”的审计事实。

Replayability

恢复后仍可继续

完整的 call/result 配对能形成确定的可重放历史，避免 provider 面对悬空请求，也让 durable session 明确知道该调用已经终止。

为什么在三个时机修复？

  • prompt_message() 前：新用户输入进入历史前，先闭合旧调用。
  • continue_() 前：恢复旧运行前，先建立完整上下文。
  • _run() 的 finally：已观察到取消时，尽早补偿。

入口前修复也覆盖了历史来自持久化存储、进程崩溃或旧版本状态，而不只是当前进程调用 cancel() 的情况。

10–14 分钟：找出应追加的消息

历史中有两个 assistant tool calls：

  • call-A: read("README.md")，已有成功的 ToolResultMessage(tool_call_id="call-A")
  • call-B: deploy("production")，没有任何 result，随后进程中断

恢复时请回答三点：

  1. Tau 应追加几条消息？
  2. 新消息的 tool_call_id 和 is_error 分别是什么？
  3. 为什么绝不能默认重新执行 call-B？
回答后展开参考答案

只追加一条消息：ToolResultMessage(tool_call_id="call-B", is_error=True)。call-A 已经闭合，重复追加会破坏一一对应关系。不能默认重试 call-B，因为崩溃点无法证明外部副作用是否已经发生；盲目重试可能重复部署。若平台要自动重试，必须另行设计幂等键、执行状态存储和工具级重试策略。

14–15 分钟：一句话检索

孤儿 tool call 的修复不是 ______，而是追加一条通过 ______ 关联、标记为 ______ 的补偿结果，从而恢复消息历史的 ______。

建议答案关键词：重试、tool_call_id、错误、完整性/可重放性。
