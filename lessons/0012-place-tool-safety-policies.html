Micro lesson 12 · Tool safety · About 15 minutes

授权、取消、隔离和错误归一化应该放在哪一层？

工具安全不是一个布尔开关。Tau 把调用前策略、实际执行、调用后治理与标准结果写回分成几个 seam；平台工程师必须同时看见这些 seam 已经保证了什么，以及它们没有保证什么。

先预测 执行管线 保证与空缺 Policy gate 完整路线

0–3 分钟：高风险工具放在哪里拦截？

模型产生：

ToolCall(
    id="call-9",
    name="deploy",
    arguments={"environment": "production"}
)

产品要求：只有拥有 deploy:production 权限且本次操作已获批准的用户才能执行。

你会优先把 gate 放在哪里？

  1. provider adapter：模型输出 tool call 时拦截
  2. before_tool_call：执行函数被调用前拦截
  3. render_call：UI 展示工具调用时拦截
  4. after_tool_call：部署完成后再检查

再预测：被 gate 拒绝后，历史中应该没有任何结果，还是应该写回标准错误结果？

3–8 分钟：读一次工具执行的安全管线

src/tau_agent/loop.py:225–305 · src/tau_agent/tools.py:15–105

  1. 先发出 start event

    ToolExecutionStartEvent 记录 call ID、工具名和参数。注意：它表示执行流程开始处理这个请求，不证明真实工具已经运行。

  2. before_tool_call 做执行前策略

    hook 接收完整 ToolCall，返回 (blocked, reason)。若被阻止，loop 不调用工具，而是创建 is_error=True 的标准结果。

  3. 检查取消、工具存在性，再执行

    已取消 → Operation aborted；未知工具 → Tool ... not found；否则调用 tool.execute(call.id, arguments, signal, on_update)。

  4. 工具异常被归一化

    普通 Exception 被转换为 AgentToolResult + is_error=True，使协议仍能写回结果。asyncio.CancelledError 特意重新抛出，不伪装成普通工具错误。

  5. after_tool_call 做结果后处理

    它会看到成功、blocked、cancelled、unknown-tool 和 exception 等路径的结果，并可返回修改后的 (result, is_error)。适合结果脱敏、统一错误包装或受信任的结果治理。

  6. 统一写回事件和消息

    无论成功还是可归一化失败，loop 都产生 ToolExecutionEndEvent 和对应的 ToolResultMessage，保持 call/result 协议完整。

8–10 分钟：区分“已有保证”与“可插入策略”

已有 · Authorization seam

可在执行前阻止

before_tool_call 是 provider-neutral 的策略入口。但 Tau 不知道租户、用户角色或审批系统；这些必须由 host 注入。

已有 · Cooperative cancellation

令牌传给工具

loop 在执行前检查 token，也把 token 传入 executor。工具若运行很久，仍需要主动观察 token；令牌本身不会强杀阻塞的外部进程。

已有 · Error boundary

异常变成标准结果

普通工具异常不会直接留下孤儿调用，而会形成可观察、可写回的错误结果。这是异常隔离，不等于安全沙箱。

空缺 · Timeout

没有内置截止时间

当前 loop 没有 per-tool timeout 参数。宿主需要包装 executor、使用超时作用域，或把调用交给具有 deadline 的独立执行服务。

空缺 · Process isolation

没有资源沙箱

except Exception 只能保护 Python 控制流，不能限制文件、网络、CPU、内存或系统调用。高风险工具应在容器、受限进程或远程 runner 中执行。

受信任边界 · Hooks

hook 自己也可能失败

before_tool_call/after_tool_call 的异常没有在该函数内归一化，因此 hook 属于受信任的 runtime policy code；生产实现应自行处理依赖故障和 fail-open/fail-closed 语义。

面试判断：“核心暴露了 hook”不等于“系统已经安全”。hook 只是策略注入点；权限来源、审批状态、租户隔离、超时和沙箱仍属于平台设计。

10–14 分钟：设计最小 production deploy gate

请设计一个 before_tool_call 策略，只描述判断流程，不需要写完整代码。要求：

  1. 非 deploy 工具直接允许；
  2. staging 部署允许；
  3. production 部署必须同时拥有权限和审批记录；
  4. 权限服务不可用时，必须明确选择 fail-open 或 fail-closed；
  5. 拒绝时返回不泄露敏感信息、但能帮助用户行动的原因。

然后回答：超时和容器隔离能否也只靠这个 hook 完成？

完成设计后展开参考结构 
if call.name != "deploy":
    return False, None

if call.arguments["environment"] != "production":
    return False, None

try:
    authorized = await permission_service.check(...)
    approved = await approval_store.has_valid_approval(...)
except DependencyUnavailable:
    return True, "Production deployment blocked: policy service unavailable"

if not authorized:
    return True, "Production deployment requires deploy permission"
if not approved:
    return True, "Production deployment requires an active approval"
return False, None

该 gate 应 fail-closed，因为无法验证高风险操作时不应执行。它可以决定“是否允许”，但不能单独提供强制超时或资源隔离；后两者需要 executor wrapper 或独立 sandbox runner。

14–15 分钟：一句话检索

before_tool_call 负责执行前 ______；after_tool_call 负责结果 ______；loop 会把普通工具异常 ______，但 timeout 与进程 sandbox 仍需由 ______ 提供。

建议答案关键词：授权/策略、治理/转换、归一化、宿主或独立执行层。
