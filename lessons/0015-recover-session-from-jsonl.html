Micro lesson 15 · Local recovery · About 15 minutes

一条本地消息何时真正可恢复？

harness 中出现过不等于已经持久化。Tau 以 MessageEndEvent 为语义边界，把完整消息和新的 active-leaf 指针追加到 JSONL；重启时再从最后一个 leaf 沿 parent 链重放。一个 session = 一个文件，一条消息 = 两行，message id 本身不足以选择历史。

3–5 分钟：先建立文件模型

src/tau_coding/session.py:1289, 2657–2661 · src/tau_coding/session_manager.py

一个 session = 一个 JSONL 文件

每个 CodingSession 对应一个 .jsonl 文件，路径来自 SessionManager 的索引记录（record.path，由 default_session_path(cwd) 推导）。文件顺序就是写入顺序。

一条消息 = 两行 entry

MessageEntry 行: {"type":"message","id":"...","parent_id":"...","message":{...canonical 消息...}}
LeafEntry    行: {"type":"leaf","id":"...","parent_id":"...","entry_id":"..."}

每一行是一个完整 JSON value，树关系完全由 parent_id 隐含。没有任何嵌套。

session 归属由文件决定：消息不存“属于哪个 session”，session 归属由文件路径决定。message 之间靠 parent_id 串成树，active branch 靠 LeafEntry 定位。

5–8 分钟：从完整消息到两条 JSONL entry

src/tau_coding/session.py:1765–1785

MessageEndEvent loop/harness 已经形成完整、规范化的 user、assistant 或 tool-result 消息。
MessageEntry 把消息 append 到 JSONL，并用 parent_id 连接当前 active path。
LeafEntry append 新的 active-branch 指针，声明恢复时应从哪一个 entry 向根回放。

实际持久化循环

for message in new_messages:            # new_messages = harness.messages[persisted_count:]
    entry = MessageEntry(
        parent_id=self._last_parent_id,   # _last_parent_id 是追加游标
        message=message,
    )
    await storage.append(entry)
    self._last_parent_id = entry.id

    leaf = LeafEntry(
        parent_id=entry.id,
        entry_id=entry.id,
    )
    await storage.append(leaf)

每个完整消息对应两次 append：一条内容记录，一条 active-leaf 记录。旧 entry 不会被原地修改。

durability boundary：MessageUpdateEvent 服务实时显示；MessageEndEvent 触发 _persist_messages_since()。因此“出现在 TUI”与“可以从 JSONL 恢复”是两个不同事实。

注意第 14 节的 append-lag：persist 写的是上一边界落进 harness.messages 的消息，不是当前事件。

8–11 分钟：load 不是反序列化一个对象，而是 replay

src/tau_coding/session.py:296–323, 367–380 · tau_agent/session/memory.py:36–103 · tree.py:22–40

  1. 按文件顺序读取全部 entries

    JsonlSessionStorage.read_all() 把每一行解析成带 type、id、parent_id 和时间戳的 SessionEntry。

  2. 找到最后 append 的 LeafEntry

    它的 entry_id 表示当前 active branch 的尾部。旧 branches 仍留在文件中，但不会自动进入当前 provider context。

  3. 从 leaf 沿 parent 链走回 root

    path_to_entry() 收集 leaf → parent → parent，检测重复 ID、缺失 entry 与 cycle，最后反转成 root-to-leaf 顺序。

  4. 把 path reduce 成 SessionState

    SessionState.from_entries() 恢复 messages、model、thinking level、label、compaction 等当前状态。

  5. 用恢复后的 messages 新建 harness

    AgentHarness(..., messages=state.messages) 得到新的进程内工作副本；旧 harness、listener、queue 与 cancellation token 不会复活。

一句话：JSONL 保存事实，LeafEntry 选择当前历史，reducer 重建状态，harness 承接新的运行时生命周期。

为什么 message id 不够？—— LeafEntry 是“选择器”

设想没有 LeafEntry，只有 MessageEntry 的 parent_id 链：文件里 E1→E2→…→E5 天然是一条线，你 branch_to_entry("E2") 后，E3/E4/E5 没有任何标记说明它们被抛弃，load 不知道该从 E5 回溯还是从 E2 回溯——分支就丢了。

有了 LeafEntry，分支后文件里多一行 LeafEntry(entry_id=E2)，它是最新的 leaf；load 找最后一个 leaf → E2 → 回溯 E1→E2。旧分支仍在文件里（可审计），但不在 active path 上。

MessageEntry 回答“发生过什么”，LeafEntry 回答“当前进行到哪”。

11–13 分钟：两类崩溃窗口

Before MessageEntry

消息只在内存中

partial delta 或尚未持久化的完整消息随进程消失。load 只能恢复旧 leaf 指向的路径。

After MessageEntry, before LeafEntry

内容在日志，指针尚未前移

新 message line 可能存在，但最后的 active leaf 仍指向旧尾部。正常 load 不会把新消息放入当前 transcript；它成为日志中可审计但不在 active path 上的 entry。

After LeafEntry

新 active path 可重放

load 找到最新 leaf 后，可以沿 parent 链恢复新消息并重新构造 harness。

Power loss

当前没有 fsync 保证

storage 使用 append 模式并在上下文退出时关闭文件，但源码没有显式 fsync。因此不能声称日志尾部在断电后一定已进入稳定存储。

用 append-lag 解释“Before MessageEntry”窗口

assistant 已经 yield 了 MessageEndEvent，但该消息可能还没被 append 进 harness.messages（append 发生在 loop.py:132，晚于 end event），也就没被 persist。此刻进程退出 → JSONL 里没有它。session.py:1606 run 结束后那次 persist 专门捕捉这条“没有后继边界”的消息。

SQLite WAL 提供了有用的对照词汇：commit-by-append 与 reopen-and-recover；SQLite Atomic Commit 则说明为什么只有写入而没有同步屏障，不能等同于 power-loss durability。Tau 当前不是 SQLite，这里只借用可靠性概念。

13–14 分钟：从日志判断恢复结果

文件依次包含：

E1  SessionInfoEntry(parent=None)
E2  MessageEntry(parent=E1, user="hello")
L2  LeafEntry(entry_id=E2)
E3  MessageEntry(parent=E2, assistant="hi")
# 进程在写 L3 前退出

请回答：

  1. 最新 LeafEntry 指向谁？
  2. path_to_entry(...) 会回放哪些 entry？
  3. 恢复后的 state.messages 包含哪些消息？
  4. E3 是否从文件中消失？它是否进入 active transcript？
  5. 如果一个 session 里既有 session_info 又有 label，它们是靠 id 找到对应 message 的吗？
回答后展开参考答案

最新 leaf 是 L2，其 entry_id=E2。恢复路径是 E1 → E2；state.messages 只有 user "hello"。E3 仍在 JSONL 中，但由于没有新的 leaf 将 active branch 指向它，正常 load 不把它放入当前 transcript。

第 5 题：不是。label 和 session_info 是 parent 链上的状态节点，靠 replay 时“状态覆盖”生效（SessionState 里 label 是最后一个 label 覆盖后的最终值，session_info 是 root 元数据）。它们从不通过 id 查找消息；session 归属由文件本身决定。
