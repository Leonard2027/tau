Micro lesson 16 · Local branching · About 15 minutes

怎样分支而不破坏历史？

分支不复制、不删除、不重写任何旧行。Tau 只做一件事：追加一条指向旧 entry 的 LeafEntry，把 active pointer 移到树中更早的位置。旧尾巴留在文件里，可审计但不在当前路径上。这条链被切断——这正是它与压缩（不断链）的本质区别。

0–3 分钟：要移动 active branch，文件里会发生什么？

JSONL 里已经积累了一条历史尾巴：

E1  SessionInfoEntry(parent=None)
E2  MessageEntry(parent=E1, user="hi")
L2  LeafEntry(entry_id=E2)
E3  MessageEntry(parent=E2, assistant="retry")
E4  MessageEntry(parent=E3, user="do it differently")
L4  LeafEntry(entry_id=E4)

用户调用 branch_to_entry("E2")，想回到 E2 重新开始。

请预测：这次调用会往文件里追加几行？每行是什么？E3、E4、L4 那几行会怎样？

判断标准：追加式日志的写法边界——不修改已存在的行。

3–7 分钟：branch_to_entry 的骨架

src/tau_coding/session.py:503–567

完整分支路径（简化）

async def branch_to_entry(self, entry_id, *, summarize=False, ...):
    if self._harness.is_running:
        raise RuntimeError(TREE_RUNNING_MESSAGE)      # 运行中禁止分支
    entries = await self._read_session_entries()
    selected_entry = by_id[entry_id]
    if not _is_branchable_tree_entry(selected_entry):
        raise ValueError(...)                          # 只接受 user/assistant/compaction/branch_summary

    target_id = entry_id
    input_prefill = None
    if summarize and abandoned_messages:
        summary_entry = BranchSummaryEntry(parent_id=entry_id, ...)
        await self._append_session_entry(summary_entry)
        target_id = summary_entry.id
    elif selected_entry 是 UserMessage:
        target_id = selected_entry.parent_id           # 回退到这条 user 消息之前
        input_prefill = selected_entry.message.text    # 并把原话预填给用户重发

    leaf = LeafEntry(parent_id=target_id, entry_id=target_id)
    await self._append_session_entry(leaf)             # 唯一的写入：一条新 leaf

    self._last_parent_id = target_id                   # 之后的追加从这里继续
    await self._refresh_persisted_state(leaf_id=target_id)
    self._harness.replace_messages(self._state.messages)

注意 LeafEntry 的 entry_id 指向 target_id——active branch 的尾部被移回到树中更早的某个 entry，而那一行 entry 从未被改动。

写入边界：整条分支路径只 append（可能先追加一条 summary，最后必追加一条 LeafEntry）。没有任何复制或改写。

7–10 分钟：三种目标解析，行为各不相同

summarize=True + 有被抛弃消息 把分支点之后的 active-path 消息压缩成 BranchSummaryEntry，target = summary 的 id，后续重放时以一段摘要代替丢失的细节。
选中 UserMessage（默认） target = 这条 user 消息的 parent_id，即回退到“这一轮之前”；input_prefill 带回原话，用户重新提问。
其余情况 target = entry_id 本身（assistant 消息、compaction、branch_summary 等），新的 active path 从该点继续。

被抛弃的消息由 _messages_after_entry_on_active_path(entries, entry_id, self._last_parent_id) 计算：它沿当前 leaf 的 parent 链找出分支点之后的全部消息（session.py:2293–2310）。

细节：分支到一条 UserMessage 并不等于“保留这条 user 消息”。它默认回退到该消息之前，并把原文预填给用户重发——所以这里的语义是“回到那一轮之前重来”，而不是“把这一轮设为起点”。

10–12 分钟：旧尾巴去哪了？

文件层面

旧行原封不动

E3、E4、L4 依然在 JSONL 里，时间戳和顺序都不变。追加式日志从不收缩。

重放层面

新 leaf 选择路径

path_to_entry(entries, new_leaf_id) 从新 leaf 沿 parent 链走回根，只包含 root → target 上的 entry；旧尾巴不在其中。

运行时层面

harness 获得新工作副本

SessionState.from_entries(entries, leaf_id=target_id) 重建 messages，harness.replace_messages(...) 换掉旧 transcript。

两个指针

_last_parent_id vs active_leaf_id

_last_parent_id 是追加游标：下一条新 entry 的 parent。leaf 里的 entry_id 是重放锚点：load/refresh 时从它回溯。分支同时更新两者。

这正是 Git 的分支模型：历史是父指针链，分支只是把“当前指针”移到已有提交上，旧提交永远留在对象库里。对照阅读 Pro Git — Branches in a Nutshell。SQLite WAL 的 commit-by-append 也共享同一思想：SQLite WAL。

12–13 分钟：分支 vs 压缩——一个切断链，一个不断链

这是最容易混淆的地方，也是面试常问的对比。两者都用“append + 移动 leaf”，但语义完全不同：

分支 branch_to_entry压缩 CompactionEntry
新 leaf 指向过去的某个 entry（如 E2）新 append 的 C
parent 链被切断——E3/E4/E5 从此不在新 leaf 的祖先链上，成为孤儿分支没切断——C 的 parent 指回最后一条消息 En，旧消息仍在链上
旧消息命运从 active path 上消失，变成可审计的孤立分支仍在 active path 的链上，只是 reducer 输出时被替换成 summary
触发用户显式调用自动（超阈值）/ 溢出 / 手动
一句话：分支 = 把 leaf 移到过去，切断链，旧分支成了孤儿；压缩 = leaf 移到新追加的 CompactionEntry 上，链不断，旧消息仍可回溯，只是 state.messages 输出时被替换。

13–14 分钟：从日志判断分支结果

继续使用本页开头的文件，调用 branch_to_entry("E2", summarize=False)：

E1  SessionInfoEntry(parent=None)
E2  MessageEntry(parent=E1, user="hi")
L2  LeafEntry(entry_id=E2)
E3  MessageEntry(parent=E2, assistant="retry")
E4  MessageEntry(parent=E3, user="do it differently")
L4  LeafEntry(entry_id=E4)

请回答：

  1. target 最终解析成哪个 id？为什么不是 E2 本身？
  2. 文件新增了哪一行？它的 parent_id 和 entry_id 分别是什么？
  3. 重放后 state.messages 里有哪些消息？（提示：active path 从哪到哪）
  4. E3、E4、L4 是否还在文件里？它们是否出现在新的 active transcript 中？
  5. 下一轮用户提问后，_last_parent_id 指向谁？新 MessageEntry 的 parent 是谁？
回答后展开参考答案

1. target = E1。因为 E2 是 UserMessage，默认分支会回退到它的 parent（E1），并把 "hi" 作为 input_prefill 交还用户重发。

2. 新增一行 LeafEntry(parent_id=E1, entry_id=E1)。唯一的新行，没有任何旧行被改写。

3. path_to_entry 走 E1，active path 上没有任何 message，所以 state.messages 为空。

4. 仍在文件里，且顺序不变；但它们不在新 leaf 的 parent 链上，所以不会进入当前 transcript。

5. _last_parent_id = E1；新 MessageEntry 的 parent 是 E1。于是树里出现两个后代分支：旧尾巴 E2→E3→E4，和新路径 E1→新消息。

14–15 分钟：一句话检索

分支不复制、不删除任何旧行，只追加一条 ______ 来把 active pointer 移到树中更早的 ______；被抛弃的消息留在文件里，成为 ______ 但不在当前 ______ 上。与压缩不同，分支 ______ 了 parent 链。

建议答案关键词：LeafEntry、entry、可审计、active path、切断。副线索：分支到 UserMessage 时，目标回退到它的 ______（答案：parent_id）。
