Micro lesson 17 · Local compaction · About 15 minutes

上下文怎样被压缩而不丢历史？

压缩不删除任何旧行、不断链。Tau 只 append 一条 CompactionEntry（含 replaces_entry_ids）并把 leaf 移到它上面；replay 时用它替换若干旧消息为一条摘要。自动/溢出压缩走“保最近 20k token”，增量压缩避免旧摘要被反复压缩。

0–3 分钟：压缩会删掉旧消息吗？

一个 session 有 10 条消息，自动压缩把前 6 条压成一段摘要。

请预测：

  1. JSONL 文件里，那 6 条旧 MessageEntry 还在吗？
  2. 压缩后 state.messages 里有几条消息？
  3. 如果之后再 branch_to_entry 回到那 6 条里的某一条，还能恢复原始消息吗？

3–6 分钟：什么时候触发压缩

自动

超阈值触发

挂在 prompt 前/后、continue 后（session.py:1560/1667/1707）。判定：有阈值、active context ≥ 2 条、context_token_estimate > threshold。

溢出

provider overflow

provider 返回 context overflow 错误时（session.py:1596）触发，压缩成功后自动重试一次（max_attempts=1）。压缩失败只记日志，不丢原轮次。

手动

用户 compact()

用户主动调用，压整个 active context（_manual_compaction_plan）。

阈值怎么定

# context_window.py:166
def auto_compaction_threshold_for_context_window(context_window_tokens):
    return max(1, context_window_tokens - DEFAULT_COMPACTION_RESERVE_TOKENS)
# DEFAULT_COMPACTION_RESERVE_TOKENS = 16_384

即：上下文窗口 − 16,384 token，提前在安全距离触发。

6–10 分钟：保最近策略（压哪些）

src/tau_coding/session.py:2037–2080 · context_window.py:23

自动和溢出都走 _recent_preserving_compaction_plan，核心是“保最近”：

# DEFAULT_COMPACTION_KEEP_RECENT_TOKENS = 20_000  (context_window.py:23)
first_kept_index = _first_recent_context_index(rows, keep_recent_tokens=20_000)
replaced = rows[:first_kept_index]   # 压最旧的这一段

# _first_recent_context_index：从尾往前累积 token
accumulated = 0
for index 从最后一条 到 最前一条:
    accumulated += estimate_message_tokens(message)
    if accumulated >= 20_000:      # 凑满 20k
        candidate_index = index
        break

保留尾部累积约 20,000 token 的消息，其余全部压缩。

边界校正（最严谨处）：20k 切点很少刚好落在消息边界，所以校准：
  • 切点命中 user 且非第一条 → 再退一格，把整条 user 提问也压掉，避免劈开
  • 切点命中非 user → 向后找下一个 user 消息作为切点
  • 找不到 user → 向后找第一个非 toolResult 消息（避免 tool result 失去它的 assistant 调用）

压缩永远切在语义干净的边界上，保证 provider 能继续消费 transcript。

10–12 分钟：压缩结果怎么落盘与替换

src/tau_coding/session.py:2060–2085 · tau_agent/session/memory.py:106–125

append 三步曲（和分支同一结构）

compaction = CompactionEntry(parent_id=self._last_parent_id,
                             summary=summary,
                             replaces_entry_ids=被压缩的旧消息 id)
await self._append_session_entry(compaction)
leaf = LeafEntry(parent_id=compaction.id, entry_id=compaction.id)
await self._append_session_entry(leaf)
self._last_parent_id = compaction.id
await self._refresh_persisted_state(leaf_id=compaction.id)
self._harness.replace_messages(self._state.messages)

replay 时 _apply_compaction（memory.py:106）把 replaces_entry_ids 指的那些旧消息替换成一条 "Previous conversation summary:\n<summary>" 的 user 摘要：

replaced_ids = set(entry.replaces_entry_ids)
for entry_id, message in message_rows:
    if entry_id not in replaced_ids:
        retained.append((entry_id, message))   # 没被压的留下
    # 被压的 → 不 append 内容，只插入一条 summary
核心洞察：compaction 不删除任何 entry。旧 MessageEntry 永远留在 JSONL 里（可审计）；它只在 replay 时，把 replaces_entry_ids 指的消息替换成摘要。state.messages 变短，但文件真相不变。

在 provider 上下文里长什么样

摘要是一条普通的 UserMessage，排在最前：

system prompt
└── [UserMessage] "Previous conversation summary:\n<结构化摘要>"   ← 压缩占位
    [UserMessage] ...最近保留的消息...
    [UserMessage] 用户新提问

格式是结构化的（## Goal / ## Constraints & Preferences / ## Progress / ## Key Decisions / ## Next Steps / ## Critical Context），目标是“让另一个 LLM 能继续工作”。

12–14 分钟：增量压缩（避免旧摘要被反复压缩）

src/tau_coding/context_window.py:204–224, 268–280 · session.py:1989–2007

第二次压缩时，旧摘要不能当普通内容重新总结——否则每压一次信息损失一层。Tau 用代码保证它从不进入待压缩内容：

# _split_previous_compaction_summary：识别并剥离旧摘要
first = messages[0]
if first 是 UserMessage 且以 "Previous conversation summary:\n" 开头:
    return 剥离前缀后的内容, messages[1:]   # (previous_summary, new_messages)

# build_compaction_summary_prompt：只序列化新消息
conversation = serialize_messages_for_compaction(new_messages)
prompt = f"<conversation>\n{conversation}\n</conversation>\n\n"
if previous_summary is not None:
    prompt += f"<previous-summary>\n{previous_summary}\n</previous-summary>\n\n"
    base_prompt = UPDATE_SUMMARIZATION_PROMPT   # ← 增量更新
else:
    base_prompt = SUMMARIZATION_PROMPT          # ← 全新总结
关键：<conversation> 里只有新消息，旧摘要绝不被重新序列化成待压缩内容。它单独放进 <previous-summary> 标签，并切换到 UPDATE_SUMMARIZATION_PROMPT —— 明确要求：
  • PRESERVE all existing information from the previous summary
  • ADD new progress, decisions, and context from the new messages
  • UPDATE Progress / Next Steps 状态

边界：如果压缩后第一条消息不是那个前缀开头的 UserMessage（例如用户压缩后马上又发了一条新 user 提问），_split_previous_compaction_summary 返回 None，走全新的 SUMMARIZATION_PROMPT，把摘要当普通内容重新总结。

14–15 分钟：从日志判断压缩结果

文件依次包含：

E1  SessionInfoEntry(parent=None)
E2  MessageEntry(parent=E1, user="setup")
E3  MessageEntry(parent=E2, assistant="ok")
E4  MessageEntry(parent=E3, user="fix bug")
E5  MessageEntry(parent=E4, assistant="done")
L5  LeafEntry(entry_id=E5)
C   CompactionEntry(parent=E5, summary="<摘要>", replaces_entry_ids=[E2, E3, E4])
Lc  LeafEntry(parent_id=C, entry_id=C)

请回答：

  1. path_to_entry(entries, C) 会经过哪些 entry？被压缩的 E2/E3/E4 还在链上吗？
  2. 重放后 state.messages 有哪些消息？（摘要长什么样）
  3. 如果之后 branch_to_entry("E3")，还能恢复原始 E2/E3 吗？重放会经过 C 吗？
  4. 第二次压缩时，如果 messages[0] 就是第一条压缩留下的摘要，会走哪个 prompt？
回答后展开参考答案

1. 会经过 C → E5 → E4 → E3 → E2 → E1。E2/E3/E4 仍在链上——C 的 parent 是 E5，链没断。

2. [UserMessage("Previous conversation summary:\n<摘要>"), UserMessage("fix bug"), AssistantMessage("done")]。E2/E3/E4 被替换成一条摘要；E5（含 E5 自己这条"done"）保留。注意：摘要占位 + E4/E5 保留消息。

3. 能。分支到 E3 → path_to_entry(entries, E3) 走 E1→E2→E3，不经过 C（C 是 E3 的后代）。原始 E2/E3 完整恢复，压缩被绕过。

4. 走 UPDATE_SUMMARIZATION_PROMPT（增量更新）。_split_previous_compaction_summary 识别前缀 → 剥到 <previous-summary> → 增量合并新消息。
